# 模块讲解 01：评分引擎（Scoring Engine）

> 对应代码：`cipherscope/core/scorer.py` | 配套测试：`tests/test_scorer.py`

---

## 一、原理篇：解决什么问题，为什么这样做

### 1.1 问题定义

CipherScope 的自动化链路是「识别 → 攻击 → 评分 → 输出」。攻击插件每尝试一个密钥就产出一段候选明文，**评分引擎要回答一个机器最难回答的问题：这段字节流是不是"人话"？**

这个问题决定了整个框架的自动化程度：
- 判得太松 → 噪声被当成明文，输出一堆乱码给用户；
- 判得太紧 → 正确结果被误杀，工具形同虚设。

### 1.2 为什么用多信号融合而不是单一指标

没有任何单一指标能可靠判定"自然语言"：

| 单一指标 | 失效场景 |
|---|---|
| 可打印字符比例 | base64 串、XOR 落于标点区的密文全部可打印 |
| 英文字母频率（卡方） | 凯撒密文的字母频率分布与明文完全一致（只是平移） |
| 词典命中 | 短文本、专业术语文本命中率低 |
| n-gram 统计 | 依赖频率表质量，表稀疏时信号整体失效 |

因此采用**六信号加权融合**：任一信号失效时，其余信号仍能托底——这是工程上的冗余设计思想在密码学场景的应用。

### 1.3 六个信号的原理

1. **flag 格式正则**（权重最高）：CTF 答案一定有格式（`flag{`、`NSSCTF{` 等）。命中即基本判定成功——这是领域知识，不是统计方法。
2. **n-gram 适应度**：自然语言的字母组合高度不均匀。英文里 "tion" 出现频率是 "qxzj" 的数万倍。对候选明文的所有连续 4 元组查频率表取 log10 概率求平均，英文约 -3.5，随机文本约 -7。这是密码学攻击的经典方法（对维吉尼亚/Playfair 的密钥搜索尤为关键）。
3. **可打印比例**：快速过滤二进制噪声，成本最低的第一道筛。
4. **常用词命中**：top-100 英文词 + CTF 高频词（flag/key/crypto），命中 5 个不同词即满分。
5. **卡方检验**：候选明文字母频率与英文标准频率的偏离度。对单表替换密码的明文最敏感。
6. **中文兜底**：UTF-8 解码后 CJK 字符占比 ≥30% 且 flag 命中 → 保底 90 分。覆盖国内赛事明文含中文的场景——英文统计模型对中文完全失效，这是设计时显式承认并处理的盲区。

### 1.4 为什么是三档裁决（SUCCESS / PROMISING / REJECT）而不是单一阈值

CTF 多层嵌套题（"base 套娃"）的中间层是英文提示语，**没有 flag 格式但质量很好**。管道需要区分：
- `SUCCESS`（找到 flag）→ 停止搜索；
- `PROMISING`（像自然语言）→ 把这段文本作为下一层输入继续解码；
- `REJECT`（噪声）→ 剪枝。

单一分数无法表达"很好但没完成"这种状态。三档裁决是管道 DFS 能正确递归的语义基础。

### 1.5 开发中实际踩过的三个坑（设计迭代的真实记录）

**坑 1：稀疏 quadgram 兜底表信号整体失效。** 初版内置约 60 组 quadgram 做兜底（完整表 25 万组需另外生成），实测英文段落命中率不足 5%，几乎所有窗口取 floor 值，fitness 被 clamp 为 0。**教训：降级方案必须验证降级后的信号依然有效，"有表"不等于"可用"。** 修复：兜底改用 trigram（同规模表覆盖率从 <5% 提升到 ~15%+）。

**坑 2：表项取"高频词"而非"字母流高频组合"。** 评分前会去掉空格拼接成连续字母流，"over the" 变成 "overthe"，产生 ert/rth/the 等跨词 trigram。初版表项按直觉填了 you/she/get 这类高频词，实测覆盖率极低。**教训：统计模型的特征必须与实际预处理方式一致——空格消除后，nde/edt/tis 这类跨词组合才是真正的高频项。**

**坑 3：信号权重必须反映信号质量。** 即便修正表项，80 组 trigram 的区分度也远不如 25 万组 quadgram。硬给兜底表同样的 25 分权重，等于让最弱的信号主导评分。修复：`_SIGNAL_WEIGHTS` 随表模式自适应——完整表模式 (25,10,15,10)，兜底模式 (8,10,25,15)，把释放的权重转给不依赖词表的 chi2 和词典信号。**这才是"优雅降级"的完整含义：不是不崩溃，而是降级后系统行为依然合理。**

## 二、代码走读篇

### 2.1 类结构与数据流

```
ScoringEngine.score(data: bytes) -> ScoreResult
  ├─ _flag_signal(text_lower)      # 信号 1: 前缀正则
  ├─ _ngram_fitness(letters)       # 信号 2: 0~25 (原始分)
  ├─ _printable_score(data)        # 信号 3: 0~10
  ├─ _word_score(text_lower)       # 信号 4: 0~15
  ├─ _chi2_score(letters)          # 信号 5: 0~10
  ├─ _chinese_ratio(data)          # 信号 6: 中文兜底
  └─ 按 _SIGNAL_WEIGHTS[表模式] 加权求 base (0~60)
       ├─ flag_hit  → score = 60 + base×(40/60), SUCCESS
       │             中文兜底: score = max(score, 90)
       └─ 无 flag   → score = base×(100/60)
                     ≥55 PROMISING / <55 REJECT
```

### 2.2 关键实现点

**`letters` 预处理**（`score()` 内）：`"".join(c for c in text_lower if c in ascii_lowercase)`——所有统计信号统一在去空格、去标点、小写化的字母流上计算。这是 §1.5 坑 2 的源头，也是理解整个模块的关键前提。

**`_load_ngrams()`**：三级查找——显式路径 → 包内 `data/quadgrams.json` → 内置 `_FALLBACK_TRIGRAMS`。返回 `(表, n)` 二元组，`n` 驱动后续窗口长度、归一化参数（`_NGRAM_PARAMS`）和权重（`_SIGNAL_WEIGHTS`）三处选择，是"模式"的载体。

**`_ngram_fitness()`**：平均 log10 概率后做**区间归一化**（`best/worst` 钳位到 [0,1] 再乘满分）。归一化参数按 n 区分：quadgram 英文典型 -3.5 / 随机 -7；trigram 英文典型 -2.2 / 兜底表下有效信号下限 -6.5。

**`_chi2_score()`**：对 26 个字母逐一计算 `(观察频率-期望频率)²/期望频率` 求和。注意它对凯撒类平移不敏感（分布形状不变）——这对"评明文"不是缺陷，因为凯撒解密后的明文分布与英文一致；但意味着它无法单独区分"明文"和"凯撒密文"，必须靠其他信号补充（§1.2 表格的实证）。

**`_word_score()`**：`set(findall(r"[a-z]+")) & COMMON_WORDS` 取**去重后**命中数——防止 "the the the the" 刷分。

**`_printable_score()`**：<70% 可打印直接记 0。阈值意义：自然语言文本可打印率接近 100%，70% 以下大概率是二进制数据。

### 2.3 性能考量

- 每候选明文评分复杂度 O(n)，四个统计信号各一遍线性扫描；
- 攻击插件可能产出数百候选（如凯撒 26 密钥 × 多路径），评分引擎是热路径——全部用内置类型和生成式表达式，无正则编译开销（正则均为字面量内联）；
- `_chinese_ratio()` 只在 flag 命中后调用，避免对每段候选做 UTF-8 全量解码。

## 三、面试问答预演篇

**Q1：你的评分引擎是怎么判断"解密成功"的？**
A：多信号加权融合 + 三档裁决。六个信号分两类：领域知识（flag 格式正则，权重最高）和统计特征（n-gram 适应度、卡方、词典命中、可打印比例）。base 分 0~60 衡量自然语言可读性，flag 命中时提到 60~100 判 SUCCESS；无 flag 但 base 折算 ≥55 判 PROMISING 让管道继续深挖；其余剪枝。三档设计是因为多层嵌套题的中间层"质量好但没完成"，单一阈值无法表达。

**Q2：卡方检验能区分凯撒密文和明文吗？**
A：不能，这是它的已知局限——凯撒是字母频率的平移，卡方值不变。所以评分引擎里卡方只是六个信号之一，凯撒密文会栽在 n-gram 和词典信号上（密文 trigram 全 miss、零常用词命中）。这也回答了为什么必须多信号融合：每个信号都有失效场景。

**Q3：quadgram 频率表 25 万组，如果部署时表文件缺失怎么办？**
A：三级降载：显式路径 → 包内默认表 → 内置 80 组 trigram 兜底表。关键设计是权重随模式自适应：检测到用兜底表时，ngram 信号权重从 25 降到 8，释放的权重转给不依赖词表的 chi2 和词典信号。这是我实际踩坑后的迭代——初版兜底表覆盖率不足 5%，信号归零，英文段落被误判为噪声。降级的标准不是"不崩溃"，是"行为依然合理"。

**Q4：为什么选择 trigram 做兜底而不是硬编码一个小 quadgram 表？**
A：覆盖率数学。26⁴≈45 万的 quadgram 空间里，60 组表对任意文本的命中率期望不足 5%；26³≈1.7 万的 trigram 空间里，同规模表覆盖率能到 15% 以上。信号有效性优先于信号精度——这是降级方案的选择原则。

**Q5：明文里有中文怎么办？英文统计模型不是全失效了吗？**
A：对，这是显式承认的盲区。设计上有中文兜底：UTF-8 解码后 CJK 字符占比 ≥30% 且 flag 命中，保底 90 分。它不评估中文文本质量，只保证"中文明文 + flag 格式"不被英文统计模型误杀。完整的中文 n-gram 评分模型在路线图上（v0.2+），可以用相同的多信号框架扩展。

**Q6：评分引擎在性能上有什么考虑？**
A：它是热路径——攻击插件每试一个密钥就要评一次。所有信号 O(n) 单遍扫描，无重复编译；中文检测（需 UTF-8 解码）延迟到 flag 命中后才执行；n-gram 查表是 dict 哈希查找。后续如果成为瓶颈，可以做多候选批处理或 Cython 化，但目前候选量级（数百）下不是瓶颈——先测量再优化。

**Q7：如果让你把通过率从 70% 提到 85%，你会动哪里？**
A：不动结构，动参数。用语料库做网格搜索：六个信号的权重、两个阈值（SUCCESS 70 / PROMISING 55）都是可调参数，以真题集通过率为目标函数自动寻优。结构上预留了 `ScoreResult.detail` 输出各信号原始分，就是为了支撑这种数据驱动的调参——这也是 v0.2 的计划。
